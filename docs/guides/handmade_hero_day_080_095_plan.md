## 目标与范围

这一阶段回答的问题是：

> 如何把丰富的地面细节稳定地画在大世界中，再让同一套软件渲染器支持缓存、绘制命令、旋转缩放、纹理采样和正确的颜色混合？

完成后应得到：

- 多张小贴图叠加生成地面，并缓存合成结果。
- 地面缓存随相机覆盖世界 chunk，支持淘汰和确定性重建，交界处没有断裂。
- 游戏先提交绘制命令，渲染器统一执行；命令及资源有明确生命周期。
- 用局部坐标轴表达旋转和缩放，完成带纹理的旋转矩形及双线性采样。
- 统一预乘 alpha 与线性光空间混合，减少透明边缘发黑和插值亮度错误。

本阶段主要增加画面表现和渲染基础。不会自动增加新敌人、武器机制、寻路或物理交互；上一阶段的跳跃、楼梯、碰撞仍是游戏玩法基础。地面纹理也不负责判定是否能走，物理继续由 Space/楼梯/碰撞体决定。

## 当前 Odin 项目的起点

| 当前证据 | 已有能力 | 本阶段差距 |
|---|---|---|
| `render.odin`、`main.odin` | CPU 写 `OffScreenBuffer`，Raylib 上传整张纹理显示 | 可继续使用此路径，无需更换后端 |
| `render_terrain.odin`、`terrain.odin` | 从 atlas 逐 tile 绘制地形；已有高台、楼梯美术 | 没有地面合成缓存；保留地形语义与现有素材 |
| `render_bitmap.odin` 的 `blend` | 直接对 8-bit RGB 做普通 alpha 混合 | 透明中间目标需要明确预乘约定；尚未做线性光空间混合 |
| `draw_image_rotated` | 以 anchor 反向旋转采样、裁剪 atlas 区域；当前为最近邻 | 不是从零做旋转；补通用轴表示、缩放和可选双线性 |
| `render_sim_region` | 遍历实体后立即绘制 | 没有统一的 push buffer；迁移时保持既有提交顺序 |
| `main.odin`、`game.odin` | 已有永久/临时 arena 和 allocator | 尚需区分跨帧缓存、长期资源、帧内 scratch |
| `animation.odin` 的 `load_aseprite_assets` | image 使用 `temp_alloc` 加载并被长期引用 | 不能直接将现有 temp arena 改为每帧清空；先处理长期资源归属 |
| `game.odin` 的 `rand.reset(12345)` | 每帧重设随机种子 | 地面生成需要独立的空间种子/随机流，避免依赖调用顺序或影响游戏随机行为 |

这些是本次检查到的状态，不假设 70–80 的待办已经实现。到实际开始本阶段时，再按代码复核一次。

### Day 081 — Creating Ground with Overlapping Bitmaps

课程页：[Day 081](https://guide.handmadehero.org/code/day081/)

**主要问题**：如何用有限的小素材合成更丰富的地面？

**功能点**：在固定地面范围内叠加底色、草地/石子、细节贴图；明确绘制层次和随机分布。本项目先在主岛内部放一块实验区域，不覆盖高台立面或越过海岸。

**先自己尝试**：用固定种子生成一小块地面，多次重画，比较图案。复用已有 atlas；缺少合适素材时先用测试图，避免素材工作阻塞渲染学习。

**完成标准**：地面细节可重现；移动人物不改变装饰位置；关闭装饰后物理行为不变。

### Day 082 — Caching Composited Bitmaps

课程页：[Day 082](https://guide.handmadehero.org/code/day082/)

**主要问题**：静态地面为什么要每帧重新叠加所有小图？

**功能点**：创建离屏 bitmap，先合成一次，再在每帧绘制合成图；记录有效状态和生成次数。

**先自己尝试**：同一固定场景切换“直接叠加”和“绘制缓存”，比较画面与合成次数。测试缓存本身带透明区域的情况，为下一集暴露重复乘 alpha 的问题。

**完成标准**：不变的区域不会每帧重新生成；缓存尺寸与内存用量明确。性能改善用计数和计时说明，不提前承诺帧率。

### Day 083 — Premultiplied Alpha

课程页：[Day 083](https://guide.handmadehero.org/code/day083/)

**主要问题**：直接画到屏幕与先画到透明中间图再合成，为什么可能不一致？

**功能点**：区分 straight alpha 与 premultiplied alpha；统一源图、中间目标和 blend 的数据约定。预乘形式的 source-over 为：

```text
C_out = C_src_premul + (1 - A_src) * C_dst_premul
A_out = A_src        + (1 - A_src) * A_dst
```

本集先理解代数；Day 094–095 再统一在线性光空间执行。不能只改 blend 而保持素材表示不变，也不能重复预乘已经转换的 atlas。

**先自己尝试**：半透明色块直接叠加与分组缓存后叠加，对照 RGB 和 alpha；允许 8-bit 量化导致的小误差。

**完成标准**：透明黑保持无贡献；透明中间结果能再合成；所有旧绘制入口明确使用哪一种表示。

### Day 085 — Transient Ground Buffers

课程页：[Day 085](https://guide.handmadehero.org/code/day085/)

**主要问题**：哪些数据可以丢弃重建，哪些只能在本帧结束后释放？

**功能点**：引入跨帧存在、可重建的 ground buffer 池；用临时内存作用域承载本帧/本次合成的工作数据。transient 不等于“全部每帧清空”。

**先自己尝试**：画出三种生命周期：素材长期存在，ground cache 跨帧复用，命令/scratch 执行后回收。审计 `load_aseprite_assets` 等所有 `temp_alloc` 用户，将仍需长期引用的图片放入合适的资源存储。

**完成标准**：重复生成/绘制后内存用量稳定；回收 scratch 不破坏图片或缓存；缓存丢弃后可重建。结构体布局变化时重启程序并重新录制回放。

### Day 090 — Bases Part I

**功能点**：理解局部坐标到输出空间的映射：`P = Origin + u * XAxis + v * YAxis`。轴的方向表示朝向，长度表示缩放。

**先自己尝试**：画出原点和两根轴，手算四角；将现有 `draw_image_rotated` 的 sin/cos 与轴表示对应。区分源码用于实体定位的 `render_basis.P` 与纹理矩形的 `XAxis/YAxis`，不是所有 basis 结构都存了旋转矩阵。

**完成标准**：能解释平移、旋转和非等比缩放如何影响四角；anchor 仍落在指定位置；本集先用调试线框验证。

### Day 091 — Bases Part II

课程页：[Day 091](https://guide.handmadehero.org/code/day091/)

### Day 094 — Converting sRGB to Light-linear Space

课程页：[Day 094](https://guide.handmadehero.org/code/day094/)

**主要问题**：为什么直接平均图片里的 RGB 数值，不等于平均光的强度？

**功能点**：采样颜色先解码到线性光空间，再插值/混合，输出时重新编码。alpha 表示覆盖/不透明度，不做 RGB 的 gamma 转换。

**先自己尝试**：对比黑白 50% 混合。若采用课程平方/开方近似，线性 0.5 编码后约为 180/255，而直接平均编码值约为 128/255。文档与函数命名明确标为近似，不称其为严格 sRGB 分段函数。

**完成标准**：数值对照符合所选转换；源与目标在同一线性空间中运算；Raylib 显示端的像素格式和输出路径经截图/色块检查，不发生重复编码。

### Day 095 — Gamma-correct Premultiplied Alpha

课程页：[Day 095](https://guide.handmadehero.org/code/day095/)

**主要问题**：预乘、颜色解码、插值和最终混合必须按什么顺序执行？

**功能点**：将 Day 083 与 Day 094 合起来：素材 RGB 先解码，再在线性空间乘 alpha；对线性预乘 RGBA 做过滤与 source-over；输出编码 RGB，alpha 仅归一化/量化。

Day 095 的加载路径把线性预乘 RGB 再编码存回 8-bit bitmap，绘制时重新解码。项目可采用这个明确约定；若选浮点线性缓存，应另算内存预算。不要混用“编码空间乘 alpha”和“线性预乘后编码”两种表示。

**先自己尝试**：用透明像素中带鲜艳 RGB 的素材测试边缘；同一图分别直接画、缓存后画、旋转过滤后画。加全局透明度时，对预乘 RGB 与 alpha 同时缩放。

**完成标准**：无透明颜色泄漏或重复乘 alpha 的暗边；缓存前后在量化误差内一致；普通贴图、旋转贴图和地面缓存使用一致的颜色约定。颜色管线改变后旧缓存全部失效并重建。

### 与现有地形和资源的衔接

- 第一版只缓存静态底层地表与装饰，保留高台立面、楼梯和需要遮挡人物的图层独立绘制。不能把所有 tile 烘成一张底图后丢失层次。
- 原型先在有界主岛内合成；随机贴图要裁剪到可显示地表，不能把海面填成陆地，也不能反向改变 Space。
- 地面缓存键至少区分 chunk 与所需层；生成规则/素材变化的版本可用于失效。材质边界、海岸与高台边缘要保持现有美术边界，不要求把所有边缘混成无缝。
- 缓存 bitmap 必须活到引用它的渲染命令执行结束。本帧先确定可见块再补齐/提交，或锁定已提交槽位，避免提交后又淘汰同一 bitmap。
- 64 块 256×256 RGBA8 图仅像素数据约 16 MiB；这只是 Day 095 配置的预算例子，不是本项目固定参数。当前临时区还承载资源，应统计总占用后再决定容量。
- 不直接依赖全局 `rand.reset`；用独立随机流和世界坐标种子生成地面。同一生成版本下，缓存生成顺序不应改变图案或游戏随机状态。
- 像素画默认保留最近邻；双线性用于学习和需要平滑的素材。完整抗锯齿、mipmap 和透视正确插值不在本阶段验收范围。
